# Counterexamples of the Quint conformance findings

Each finding of the conformance work on `impl/` (`formal/quint/CONFORMANCE.md`) was checked by building its input on the current code and running it. Verdicts:

- **CONFIRMED**: the code accepts the input the finding describes, or refuses an honest input.
- **NOT REPRODUCED**: the code refuses the input; the refusing check is named.
- **GUARD HOLDS**: the attack the finding says is refused is refused.
- **OPEN DESIGN**: the code and the model differ where `design/SCHEME.md` does not decide; both are safe. "closed by decision" names the DECISIONS entry that fixed the rule in the code and the model.

| ID | Finding | Input run on the code | Result | Verdict | Resolution |
|---|---|---|---|---|---|
| M1 | The model let an honest old-committee node post RS_DEAL after HANDOVER. HANDOVER erases the transferred shares of the old committee (SCHEME section 5, "Old nodes erase transferred shares when HANDOVER is on the board"), so the node would deal shares it no longer holds. Found by the replay: the Rust board refused an honest model step. | `tests/quint-regressions/deal-after-handover.itf.json` (n = 4: MSG, 3 ACK, ROTATE reshare, RS_DEAL 1 and 2, 3 READY, then RS_DEAL 3), replayed step by step on `Board` and `NodeState` by `regression_m1_old_node_cannot_deal_after_handover` in `impl/tests/quint_conformance.rs`. | `Board::apply(Event::Dealer)` returns `Handover` for the late deal; HANDOVER, Q = {1, 2} and every node record stay unchanged. | GUARD HOLDS | Model fixed: `holdsShares` guard in `honestReshareDeal`. Quint test `dealAfterHandoverTest` fails on the pre-fix model and passes after. The same Rust test shows that the trace is a mismatch when replayed as a trace of the fixed model. |
| G1 | A FINAL or VOID post that is invalid when it arrives (the spend is not yet on the chain, or its committee does not serve the request) is dropped by Rust for good. | E1 | The doc comment of `builder::select_utxo` said that the board enforces generation eligibility (the delay Δ and the trigger). The trigger and the fee rule are not monotone in height, so the anchor block itself can still be ineligible; honest nodes then NACK it and the attempt fails (the scripted conformance trace `failedAttemptScenario` replays this case on the code). The OBS-side check is a caller input in `impl/` (CONFORMANCE.md section 4). No ITF regression trace: the fix is a doc comment, and the model gates honest OBS on eligibility, so no model trace has an honest OBS below Δ; the unit test pins the board behaviour instead. |

## Batched Midnight writes (`design/enhancement/quint/batched_checkpoint.qnt`)

`impl/` holds the board of base line dealing only. It has no Midnight checkpoint, no settlement, no board-first call and no committee nonce pool, so no finding of this model can be built on it. The Sessions prototype `proto/sessions-sim` holds the checkpoint pool fields: its tests `pending_min_restart_jump_refused_and_accepted` and `sequential_pending_membership_requires_matching_root` cover the `pending_min` rule of this model (Sessions D-034). The model's design run shows no violation of any invariant.

| ID | Finding | Input run on the code | Result | Verdict | Resolution |
|---|---|---|---|---|---|
| B1 | A board-first call is in force at its board order, and until the next checkpoint lands it exists only on the board. A whole-committee restart that rolls back every disk and loses the board tail past the latest landed checkpoint forgets the call and its pending `nf`, so a second call on the same `nf` comes into force. `C11_bfNoDupInForce` fails in module `boardLoss`. `C11_bfOneHostSpend` holds: the pinned host input still confirms once. | none: `impl/` has no board-first state. Trace: `design/enhancement/quint/runs/batched-boardLoss.itf.json`. | not run | OPEN DESIGN | DESIGN §5.3 rests board-first single use on the board, and C11 on the pinned input. DECISIONS 52 states the case as a consequence. O29 keeps it: a proof of C11 for board-first charters must cover a restart with a lost board tail. A board-first reissue's carried VOID settlement is in the same position until its `bf_root` lands (DESIGN §5.6). |
| B2 | The model lets a host transaction confirm only while its request is live. A request that ends RELEASED and whose transaction confirms later settles RELEASED, so the record stays locked to the spent pinned input and its change record gets no Midnight record. Batching does not change this: the per-request `settle` had the same rule. | none: `impl/` has no settlement state. | not run | OPEN DESIGN | DESIGN §5.6 does not say how a RELEASED record moves to its change record after a late confirmation. Left to the `FenrirAssets` contract design (§14.3). |

## Split-line dealing on the prototype (`formal/quint/splitline.qnt`, `splitline_pools.qnt`)

The split-line prototype is `impl/src/split/` with the reducer `SplitBoard` in `state.rs`. `impl/tests/quint_split_conformance.rs` replays the traces in `tests/quint-regressions/splitline/`, which are byte copies of the item 26 exports. The model-side verdicts are in the model's own findings file. The verdicts below concern the prototype. The prototype has no whole-committee restart, no recovery reshare, no cold start, no seat logs and no `slot_bind`, so a trace that needs one of these rules cannot run on it. Such a row is OPEN DESIGN and names the missing rule.
